    Spec vs. mirror: choosing doc-first, code-first, or atomic¶

    Draft status

    This post is part of the Track E orchestrator series and is not yet published.

    A documentation change is never just "the docs."

    In this project, every ticket that changes both docs and code has to answer a more specific question: is the doc a spec, or is it a mirror?

    A spec is prescriptive. It is the contract the implementation must satisfy. The code is correct only if it follows the doc.

    A mirror is descriptive. It records the behavior that already exists, or the shape the implementation found after it was built. The doc is correct only if it matches the code.

    That sounds like a small writing distinction. In an automated build loop, it is not small. It decides commit order, review expectations, and whether a later agent can treat the prose as an input dependency or only as a receipt.

    That is why tickets can carry a doc_mode: field.

    The three modes¶

    The authoring contract names three possible shapes:

    Mode Role of the doc Commit shape
    spec-first The doc is a prescriptive contract. Write the doc first, then make code satisfy it.
    code-first The doc is a descriptive mirror of as-built behavior. Build the code first, then update docs in the same PR.
    atomic The doc and code are already coupled. Land both sides together.

    Use doc_mode: spec-first when the doc is the interface another ticket will consume, or when the change is large or risky enough that the prose must become the acceptance contract before implementation starts. Game design docs feeding an engine, screen specs feeding UI work, and protocol contracts fit here.

    Use doc_mode: code-first when the right shape is not known until the code is built. Exploratory implementation notes and docs that explain internal structure after it exists belong here.

    Use doc_mode: atomic when separating the two sides would make the primary branch misleading. Some surfaces are not "doc first" or "code first"; they are a paired edit. A rule edit and the enforcement surface it describes can be that kind of coupled change. So can an annotation update that must remain true of the source unit it annotates.

    The field is optional. A documentation-only ticket, or a code-only ticket, has no meaningful doc/code ordering requirement and should omit it.

    Two opposite ways docs rot¶

    The modes exist because the two single-ordering choices fail in opposite directions.

    Spec-first can rot forward. The project can gain beautiful documents for code that never ships, or for code that ships differently. That is speculative doc rot: the prose is ahead of reality and teaches agents the wrong contract.

    Code-first can rot backward. The implementation changes, the mirror does not catch up, and future readers inherit a stale description of behavior that no longer exists.

    Atomic closes the window when the two sides are already known to be coupled. It does not claim one side is conceptually first. It says the repository should not observe either side alone.

    This is the distinction the anatomy of a ticket post keeps circling from another angle: the ticket is a machine-readable contract, not a suggestion written near the work. doc_mode: is one more field where that contract stops being prose and starts controlling how the run is judged.

    Automation changes the category¶

    On a human team, "write the spec first" is usually etiquette. A senior reviewer might notice that a branch implemented code before its design doc, but most teams do not police that order mechanically. By the time the PR is open, the branch often just looks like a pile of final files.

    Here, doc_mode: is machine-readable frontmatter, and one case already has a merge-time check.

    lint-doc-mode-order runs only for ticket branches whose resolved ticket sets doc_mode: spec-first. It walks the branch commits from the primary branch to HEAD. If the first code-touching commit comes before the first doc-touching commit, the lint fails. A single commit that touches both docs and code is allowed.

    The details matter:

    • Doc paths are docs/**, workflow/docs/**, AGENTS.md, and CLAUDE.md.
    • Code paths are everything else, except ticket and run-record markdown under tickets/backlog/** or tickets/phase-*/**.
    • The check skips non-ticket branches, tickets without doc_mode:, code-first tickets, atomic tickets, unrecognized values, and clones where the primary branch ref cannot be resolved.

    So the shipped enforcement today is precise and deliberately limited. Only spec-first has an order gate, because that is the mode where commit order is mechanically checkable: the contract must appear before the first code that claims to implement it.

    That makes spec-first docs different from normal prose. A later ticket can depend on the document as build input. If the doc is wrong, missing, or out of order, that is not merely a documentation smell. It is a broken dependency in the same graph the orchestrator uses to schedule work.

    This is also why the mechanism belongs next to the docs-as-code story in Docs are first-class, just like the code and the tests. Doc frontmatter already gives documentation a typed role in the repo's graph. doc_mode: gives a ticket one typed claim about how that doc relates to the code it is changing.

    What the recorded intent can unlock¶

    The important word is can.

    Today, only spec-first has a specific gate. code-first and atomic are still valuable because they record intent in a stable place. That intent is latent tooling surface, not shipped behavior.

    Once tickets reliably say which role a doc plays, several downstream checks become possible:

    • Scheduling. Spec-first doc tickets can run before consumers because their output is a contract other agents can build from.
    • Drift detection. Code-first tickets can be scanned later for mirrors that failed to follow the implementation they describe.
    • Review routing. A spec-first doc deserves different attention from a code-first mirror. One is an input contract; the other is an accuracy check against shipped behavior.
    • Training signal. Predicted doc role can be compared with what happened in the run record: did the contract hold, did the mirror lag, did atomic work actually land as one coupled change?

    Those are not all implemented today. The point of the field is that they become implementable without rereading every ticket as English. The distinction is already captured where the scheduler, lints, review tools, and future agents can find it.

    That is the larger lesson: automation turns "we should probably write the doc first" into a dependency contract. The value is not that the repository loves paperwork. The value is that an autonomous agent can tell whether a document is the thing it must obey, the thing it must update after building, or the thing it must keep coupled to code in the same edit.

    Spec, mirror, or atomic is not a matter of taste. It is how the build loop knows what kind of truth the document is supposed to carry.

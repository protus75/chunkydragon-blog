    The overcorrection pendulum: every agent rule I wrote to fix the last one¶

    The agent rules in this repo look, from a distance, like a pile of scars.

    That is not wrong. A rule lands because something went wrong in a real run: an agent patched the symptom and skipped the cause, noticed a second problem and folded it into the current diff, filed a fix ticket that the scheduler ignored, or got so committed to root-cause hunting that it forgot the immediate thing I asked for.

    But the more interesting pattern is not "the rules got stricter." It is that each correction pushed the agent toward the next failure mode. The contract did not evolve in a straight line from loose to strict. It swung. Each new rule fixed the last kind of bad judgment and over-weighted a different one.

    This is the capstone to a few earlier posts. Don't fold it in argues that a second problem belongs in its own ticket instead of the current diff. From surprise to rule to skill explains how an incident graduates into the durable agent contract. A rule an agent can't argue with explains why the strongest rules fail closed. This post is the arc between them: what happened when the rules started correcting each other.

    First swing: stop treating the symptom as the job¶

    The early failure was ordinary engineering tunnel vision, made worse by an agent's context window. A run failed. The agent fixed the local error or edited the ticket enough to pass the next command. The immediate symptom moved, but the class of failure stayed alive for the next ticket to rediscover.

    So the rule moved hard in the other direction. CLAUDE.md now has Diagnose a failed ticket's root cause before any edit or rerun, and the history entry with the same heading is explicit about the order: diagnose the failed run, name the root cause in one sentence, correct the cause, then rerun. Beside it is Propose the class-level prevention, not just the instance fix, which asks the agent, every time it fixes or diagnoses a concrete problem, what standing change would stop the whole class from recurring.

    That was the right correction. A failed lint, a broken workflow step, or a stalled ticket is rarely only the local red line. There is usually a generator, template, dependency edge, gate, or rule surface behind it. If the agent only clears the visible error, it exports the same problem to the next autonomous run.

    But this rule also taught the agent a dangerous lesson: the cause is always more important than the instance. That is true often enough to feel safe and false often enough to hurt.

    Second swing: don't raise questions and forget them¶

    The next failure was not too little diagnosis. It was conversational drift.

    An agent would raise three things in one reply: one concrete fix, one possible follow-up, and one question for later. The user would answer one of them. The agent would move forward and silently drop the rest. Nothing in the code failed. The failure lived in the thread.

    So the contract gained Track and re-surface open threads; never drop parked questions. The rule says that when a reply raises more than one question, option, or next step, those become an open list the agent owns until each item is explicitly resolved or completed. Acting on one thread does not resolve the others. Every reply that still has open threads must restate them.

    This fixed a real trust problem. It made "later" mean something in chat instead of letting it decay into transcript fog. It also rhymed with the backlog habit from Don't fold it in: if a second concern is real, it needs a durable surface.

    But again, the correction had a shadow. Once the agent learned not to drop threads, it started treating every related concern as something that had to stay active in the present moment. The system had made forgetting harder. It had not yet taught priority.

    Third swing: make the scheduler respect the fix¶

    Then the same failure showed up one layer lower. Agents had learned to file fix tickets. The backlog had a real artifact. The problem was that the scheduler could still run the broken tickets again before the fix ticket landed.

    Prose was not enough here. "This ticket should run after that one" is a sentence for a human, not an input to the planner. So the rule became A fix ticket MUST wire its dependency into every existing ticket it unblocks. When an agent authors a ticket that fixes a defect in tooling, a lint, a generator, a shared module, or a fixture format, it must identify existing affected tickets and add the fix ticket's stem to their ## Depends on sections. If the failure was a file collision, it must also encode the serialization edge in ## Touches or ## Depends on.

    This is the Find every surface related to X lesson applied to scheduling. The durable artifact is only useful if every surface that consumes it points at it. A fix ticket that is not wired into the tickets it unblocks is a note, not a control-plane fact.

    That rule closed a recurrence loop. It also reinforced the same bias: when you see a cause, chase it into every dependent surface right now.

    Fourth swing: root-cause zeal became paralysis¶

    At that point the agent contract had trained a strong reflex:

    • diagnose before rerun;
    • propose the class-level prevention;
    • never drop open threads;
    • author every real follow-up;
    • wire every unblocked ticket.

    Each piece was justified. Together, they created a new failure mode. In an interactive chat, the agent could receive a small, urgent request and disappear into cause analysis, dependency sweeps, and unsolicited ticket authoring before doing the thing that was broken in front of the owner.

    The fix was In interactive chat, announce and confirm before any unsolicited ticket-authoring dive. The rule does not say root-cause work is bad. It says unrequested ticket-worthy tangents must be named before the agent dives: explain the finding, say why it merits a ticket, and ask whether to author now, author after the current task, or skip. For longer unsolicited investigations, even the research gets a visibility floor first.

    This was the pendulum at its clearest. A rule set built to stop agents from band-aiding symptoms had taught them to treat every root cause as immediately urgent. The new rule separated importance from timing. A cause can matter without preempting the current ask.

    The synthesis: urgency and importance are different axes¶

    The latest correction is the one that finally names the two axes the agent kept collapsing. CLAUDE.md now has In interactive chat, split a reported problem into an instance-fix ticket (authored first) and a cause-fix ticket (captured, never dropped).

    That rule is deliberately two-step. When a reported problem exposes both something broken now and a recurring cause, the agent authors the immediate instance-fix ticket first. Then it authors the cause-fix ticket as a separate file. The instance unblocks the reported symptom. The cause is captured and routed, but it is not folded into the instance and it is not allowed to disappear.

    That is the synthesis the earlier rules were reaching for:

    • urgent does not mean important enough to absorb every related cause;
    • important does not mean urgent enough to delay the immediate unblock;
    • "later" is acceptable only when the work is encoded somewhere the system can schedule;
    • ordering belongs in fields like priority:, batch_prerequisite:, and ## Depends on, not in prose.

    The honest edge is that this is not solved in the sense of finished. It is a standing tuning discipline. The project still needs the root-cause rule, the prevention rule, the open-thread rule, the dependency-wiring rule, and the unsolicited-authoring pause. Remove any one of them and the pendulum swings back toward the failure it was written to stop.

    What changed is the frame. The agent is no longer being told "always chase the cause" or "always stay on the instance." It is being told to preserve both truths without merging them. Do the urgent thing first when the owner reported a broken instance. Capture the important cause second so it cannot be forgotten. Use the backlog and dependency graph to hold the relationship after the chat turn ends.

    That is what the rule evolution was really about. Not more severity. Better separation.
